# Cognito compatibility program

This document is the completion contract for the native Cognito implementation. It is a
roadmap, not a support claim. A row is complete only after its API behavior, persistence,
cleanup, CloudFormation/CDK lifecycle, and client interoperability gates have passed.

## Current qualification boundary

The implementation is still under active qualification. Passing unit tests or registering an
operation in the dispatcher does not complete this program. In particular:

- Amplify v6 direct protocol and Expo Web UI flows have passed against isolated Docker images,
  and the Amplify Android 2.39.0 protocol gate passes on a hermetic Robolectric JVM. The
  Swift/macOS gate is still qualification work: it requires a host that accepts the harness's
  keychain entitlement signature, because macOS 26 kills ad-hoc restricted signatures at launch
  (amfid error -424) and the Amplify keychain store cannot run without `keychain-access-groups`,
  so the gate skips on such hosts until a provisioned signing identity is available. None of
  these are evidence for iOS Simulator, Android emulator, device, or native Authenticator UI
  support.
- WebAuthn cryptography and SDK handlers have unit coverage, and
  `tests/unit/services/cognito_idp/test_webauthn_chrome.py` drives a real Chrome virtual
  authenticator through registration and sign-in over the local TLS/RP-origin boundary on
  macOS. Repeating that gate in CI and on other platforms remains qualification work.
- Managed-login branding and terms must visibly and safely change the rendered pages; gateway
  evidence now exists in `tests/aws/services/cognito_idp/test_hosted_ui_rendering.py`, which
  compares branded and uncustomized `/login`, `/signup`, and classic pages through the real
  gateway. Persisting API payloads without rendering the result is not support.
- User-import jobs must accept a bounded upload through the returned local presigned URL, execute
  the CSV state machine, and create AWS-shaped `RESET_REQUIRED` users, with log delivery to the
  configured local destination; gateway evidence now exists in
  `tests/aws/services/cognito_idp/test_user_import.py`. Storage-only implementations do not pass
  these gates.
- A final service-wide claim additionally requires regeneration of capability evidence, one clean
  Docker image, restart coverage, the full regression suite, and zero owned-resource residue.

## Target clients

The primary real-world fixture is `billgym/apps/infra` together with its Expo application.
It uses Amplify v6 on Web/PWA, iOS, and Android with an existing CDK-managed user pool.
Its required contract is:

- email sign-in through `USER_SRP_AUTH`;
- admin-created users and `NEW_PASSWORD_REQUIRED` on first sign-in;
- optional software-token TOTP MFA;
- `AdminCreateUser`, `AdminGetUser`, `AdminSetUserPassword`, and group membership;
- `admin`, `trainer`, and `member` groups in access and ID token claims;
- pre-token-generation and post-confirmation Lambda triggers;
- custom `tenantId`, with client write access denied and token read access allowed;
- one-hour access/ID tokens, 30-day refresh tokens, refresh and revocation;
- API Gateway HTTP API JWT authorization with the same issuer, audience, and JWKS;
- no public sign-up and no client secret in Web/Mobile applications.

The current `BillgymAuth` synthesis contains exactly five Cognito resources: one
`AWS::Cognito::UserPool`, one `AWS::Cognito::UserPoolClient`, and three
`AWS::Cognito::UserPoolGroup` resources. The pool contract includes email aliases and
verification, admin-only creation, password policy, optional software-token MFA, custom
`tenantId`, tags, Retain policies, and pre-token/post-confirmation Lambda configuration. The
client contract includes SRP and refresh auth, read/write attribute restrictions,
`PreventUserExistenceErrors`, minute-based token-validity units, callback URLs, the `code` and
`implicit` OAuth flow declarations generated by the current CDK, and the standard OpenID
scopes. The Docker CDK gate must deploy this exact shape rather than a reduced substitute.

Hosted UI is a second, independent interoperability target. It must support OAuth 2.0
Authorization Code with PKCE for public clients, OIDC discovery/JWKS, refresh, revocation,
logout, callbacks, cookies, state and nonce validation, and federation without weakening the
direct Amplify SRP flow.

## Delivery tracks

| Track | Required behavior | Completion gate |
| --- | --- | --- |
| User-pool control plane | Full pool, client, user, group, resource-server, domain, IdP, device, tag, import, and risk-configuration lifecycle | Every supported Botocore operation has local/AWS differential tests, pagination, bounds, isolation, and restart coverage |
| Authentication | Password, SRP, admin auth, refresh, challenge sessions, password reset, confirmation, MFA, devices, custom auth, and passkeys where the AWS model exposes them | Amplify v6 Web/iOS/Android and AWS SDK clients complete the same challenge sequences |
| Tokens and OIDC | Separate RS256 keys, rotation, AWS-shaped claims, JWKS, discovery, userInfo, revoke, logout, and strict issuer/audience validation | Independent JWT/OIDC validators pass; replay, expiry, cross-pool and algorithm-confusion tests fail closed |
| Hosted UI and federation | Login/consent, code+PKCE, cookies/CSRF, custom domains, Google/Apple/OIDC/SAML federation, callbacks, and logout | Browser tests exercise success, cancellation, replay, invalid redirect, and provider errors |
| Identity pools | Pool/role/principal-tag lifecycle, identity linking, authenticated/guest identities, temporary STS credentials, merge/unlink, developer identities, tags, and pagination | Returned credentials identify the correct assumed role/account and work against allowed local AWS APIs |
| Cognito Sync | Datasets, records, sync sessions, conflicts, pagination, usage, device subscriptions, bulk publish, events, and configuration | Version/conflict semantics and offline synchronization pass differential and restart tests |
| CloudFormation/CDK | All `AWS::Cognito::*` resources, attributes, replacement rules, rollback, retain policies, and drift-safe read/update/delete | Real CDK CLI deploy/update/no-op/rollback/destroy passes in Docker with zero residual resources |
| Durability and operations | Save/load, process/container restart, key/session recovery, concurrency, quotas, bounded memory, audit-safe logging, and metrics | Restart and stress suites pass without plaintext secrets, stale indexes, leaks, hangs, or false success |

## Promotion rules

- Never infer service-wide support from a single API, resource, language binding, or happy path.
- Unsupported request fields and operations fail explicitly; they never disappear silently into a
  permissive fallback.
- Tests that create resources use fixtures and prove cleanup. AWS-validated tests use snapshots
  generated by AWS and never hand-edit snapshot data.
- Public clients never receive or persist private signing keys, password material, or raw refresh
  tokens in service state; stored refresh and authorization codes are content hashes.
- Cross-account, cross-region, cross-pool, stale-session, replay, and identity-replacement paths
  fail closed before mutation.
- “Amplify-compatible” requires the unmodified Amplify client to pass on Web, iOS, and Android.
- The current Amplify v6 direct User Pool client has no supported general-purpose endpoint
  override. Direct SRP tests therefore use a test-owned transport proxy/DNS adapter that rewrites
  the AWS Cognito origin to LocalStack without changing Amplify protocol code; the adapter must
  deny real AWS egress and is part of the evidence boundary.
- “Complete” requires Cognito IDP, Identity, Sync, CloudFormation/CDK, restart, and Docker gates;
  an implementation-only unit suite is insufficient.

## Execution order

1. Harden the native user-pool/JWT/JWKS foundation and prove persistence.
2. Complete Hosted UI code+PKCE and the direct SRP/challenge/TOTP paths in parallel.
3. Add groups, attributes, triggers, devices, recovery, and the remaining user-pool APIs.
4. Complete all Cognito CloudFormation providers and the real CDK lifecycle gate.
5. Implement Identity Pools with strict User Pool JWT verification and real local STS roles.
6. Implement Cognito Sync with versioned conflict semantics.
7. Run Amplify Web, iOS, and Android clients plus the Billgym CDK/app fixture in Docker.
8. Run AWS differential, restart, concurrency, security, and resource-budget suites before any
   service-wide promotion.

## Local end-to-end fixture

A runnable local E2E exercises the HTTP API JWT path end to end against this fork:

- `scripts/e2e_cdk_deploy.py` deploys the `EnterpriseHttpApiJwt` fixture
  (`tests/aws/cli/fixtures/cdk_apps/python/enterprise_http_api_jwt.py`) with the real,
  pinned CDK CLI through `localstack.cli.cdk.launch_cdk`, against a host-mode
  LocalStack started with `python -m localstack.runtime.main`. Outputs land in
  `e2e-front/cdk-outputs.json` (git-ignored, regenerable).
- `scripts/e2e_seed_demo_user.py` seeds a demo user/group from those outputs and
  smoke-tests the browser paths (Cognito preflight, `InitiateAuth`, JWT API call).
- `e2e-front/` is a Next.js app using the official Amplify UI (`<Authenticator>`,
  `USER_SRP_AUTH`). The browser never leaves its own origin: `next.config.ts`
  rewrites proxy `/ls-cognito/*` to the local gateway and `/ls-api/*` to the
  path-based HTTP API invoke URL, so no CORS configuration or DNS/TLS adapter is
  needed on any dev port. Amplify's `userPoolEndpoint` (aws-amplify >= v6.20)
  points at the same-origin prefix. See `e2e-front/README.md` for the runbook.

This fixture is a development convenience; it does not replace the Docker CDK gate
or the client qualification tracks above.

The layered CDK gate architecture (synth, in-process deploy, Docker lifecycle with
`scripts/run_cdk_docker_gate.sh`, bootstrap/DefaultStackSynthesizer) and the measured
restart-persistence boundary are documented in `docs/cdk-localstack-enterprise.md`.

Official contracts used by this program include the AWS Cognito User Pools and Federated
Identities API references, the CloudFormation Cognito resource reference, and current Amplify
Auth documentation. Repository tests remain the executable source of truth.
